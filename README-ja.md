# fortune-gatekeeper（占いMCP）

Claude が会話の流れから直接「占いを引ける」ようにする MCP サーバー。Cloudflare Workers の上で動く、一本の直通電話。公開の**カード層**（カード占い6デッキ・易占（周易）・アストロダイス・ジオマンシー・月まわりの暦・逆引きホロスコープ）と、鍵つきの**占星術層**（ホロスコープ計算・シナストリー・数秘術・宿曜・四柱推命・九星気学）が入っています。

**引く（立てる・計算する）のはサーバー、読むのは Claude。** ここには解釈層がありません。シャッフルも正逆も飛び出しも、易の六爻もサーバー側の乱数（`crypto.getRandomValues`）で決めて、その結果だけを返します。LLM に引かせると「引いたふり」ができてしまうので、乱数だけは渡さない、という設計です。

カード層と易占には守るべき API キーもコストも無いので、認証・アクセス制御を持ちません（誰が呼んでも同じ答えが返ります）。占星術層だけは「誰のチャートか」を分ける必要があるため、別の入口にしてあります——OAuth（Cloudflare Access で身元を確かめる `POST /astro/mcp`）の1本だけです（後述）。

**公開層には個人データの口を生やしません。** 乱数で引くだけの層（カード・易・アストロダイス・ジオマンシー）と、誰の誕生日も場所も受け取らない月まわりの暦（`moon_calendar`）と逆引きホロスコープ（`reverse_horoscope`）は何も預からないので公開のまま、**誕生日を使う占い（数秘術・宿曜など）は鍵つきの占星術層だけ**に置いています。

**鍵つきの入口はスーパーセットです**（2026-08-24）。`POST /astro/mcp` には占星術層 20 本に加えて公開層の 7 ツールもそのまま同居していて、MCP コネクタを 1 個しか登録できないプランでも、鍵側 1 本の接続で全 27 ツールに届きます。逆方向はありません——公開層に鍵つき層のツールは載りません（公開層のコードが占星術層から借りるのは天体計算の純部品だけで、台帳（KV）・認証・鍵つきツールのモジュールには触れない作りです）。カード系は鍵つきの入口から引いても**何も保存されません**——委譲先のカード層コードには台帳（KV）も身元も渡らないので、匿名の入口と性質が変わりません。

易占（周易）はデッキではなく別ツール（[`cast_hexagram`](#cast_hexagram)）です。六十四卦から1卦を立てて**卦名・番号・記号・爻の並びだけ**を返し、卦辞・爻辞は同梱しません。アストロダイス（[`roll_astro_dice`](#roll_astro_dice)）も同様にデッキではなく、天体・星座・ハウスの 12 面ダイス 3 個を振って**名前と記号の組だけ**を返します。ジオマンシー（[`cast_geomancy`](#cast_geomancy)）はシールドチャート一式を立て、**16 図形の名前と点の並びだけ**を返します。数秘術（[`calculate_numerology`](#calculate_numerology)）は乱数を1ビットも使わず生年月日から**数と途中式だけ**を返しますが、誕生日を使うので公開のカード層には置いていません（鍵つきの占星術層にあります）。

### なぜデッキで厚さが違うか

空オラクルとエニグマオラクルは、このサーバーの作者（和条門尚樹）の自作オラクルデッキです。世に出回っていない＝**LLM の学習データに無い**ので、サーバー側が一言と解説を持って渡さないと Claude は読みようがありません。だから2デッキだけ中身が厚い。

逆にタロット・ルーン・ルノルマン・易の六十四卦は広く知られた体系で、Claude が自分の知識で読めます。こちらはカード名（卦名）だけを返し、意味は同梱しません。権利の線引き（`PUBLIC_MEANINGS`）とも向きが揃っていて、**知られているものは名前だけ、知られていないものは意味ごと**、という一本の理屈になっています。この線引きは `initialize` の `instructions`・`list_decks` の案内文・`draw_cards` の説明文の3箇所に書いてあるので、Claude 側もそのつもりで読みます。

「意味テキスト」は一言（`meaning` / `meaning_upright` / `meaning_reversed`）、「解説」はそれより長い一段落（`explanation` / `explanation_upright` / `explanation_reversed`）。解説の素材は `meanings/` にあります（後述）。

`tarot_full` は大アルカナ22枚＋小アルカナ56枚のフルデッキ。素材は `tarot-major.json` と `tarot-minor.json` の2枚で、`decks.ts` が読み込み時に合成します（枚数が 78 にならなければその場で落ちる）。小アルカナ単体は引けるデッキとして出していません。

タロットとルーンは意味テキストの出自確認が済むまで公開版に載せません。カード名と正逆だけが返るので、そこは Claude 自身の知識で読みます。可否の管理は `scripts/sync-decks.mjs` 冒頭の `PUBLIC_MEANINGS` 一箇所。

空オラクルは小説こぼれ話のお題出し係も兼ねていて、題の形式が「カード名『メッセージ』」です。テキスト出力はこの形を崩さないようにしてあります。

## ツール

### `list_decks`

引数なし。デッキ一覧（id / name / card_count / has_reversed / meanings_included）とスプレッド一覧（id / name / count / positions）を返す。

### `draw_cards`

| 引数 | 型 | 既定 | 説明 |
|---|---|---|---|
| `deck` | enum（必須） | — | `sky` / `enigma` / `tarot` / `tarot_full` / `rune` |
| `count` | integer | 1 | 引く枚数。デッキ枚数を超えるとエラー |
| `spread` | enum | — | 指定すると枚数が固定され、各札に位置が付く（`count` より優先） |
| `allow_reversed` | boolean | true | false で全部正位置。もともと正逆の無いカードは常に正位置 |
| `jump_out` | boolean | true | 飛び出しカード。false で必ず 0 枚 |

飛び出し（ジャンプアウト）はシャッフル中に落ちた札の再現で、0枚92 / 1枚6.5 / 2枚3 / 3枚1 の重みで 0〜3 枚。本引きとは別枠で、札は重複しません（山が足りないときは飛び出しを削って本引きを優先）。

テキスト出力の形:

```
空オラクル / 3枚引き
1. 過去: 星空『自分を甘やかして、ゆっくり寝る時間です』
   解説: 星空のオラクルが示すのは空に瞬く星々、つまり気持ちのいい夜の象徴です。……
2. 現在: 霧『心の奥底の望みに耳を傾けましょう』
   解説: 五里霧中、周りの雑音が煩わしくても、だからこそ深く深く潜りましょう。……
3. 未来: 虹『今までの頑張りが報われるでしょう』
   解説: 虹のオラクルが示すのは、雨が上がった爽やかな空、夢への架け橋。……
飛び出し: 雷『サプライズがあるかもしれません』
   解説: 晴天の霹靂、とはよく言ったもの。何か、サプライズがあるかもしれません。……
```

解説を持つデッキでは、札の行の直下に `   解説: …`（半角スペース3つ）が1行ぶら下がります。**お題形式「カード名『メッセージ』」の行はそのまま**で、解説は別行に逃がしてあります。飛び出しも解説があるときだけ1枚ずつ行を分け、解説を持たないデッキ（タロット・ルーン）では従来どおり `飛び出し: 月（逆位置）、星（正位置）` の1行にまとまります。

同じ内容が `structuredContent` にも構造化されて載ります（各札の `explanation`。解説を持たないデッキではキーごと省かれます）。

### `cast_hexagram`

易占（周易）の卦を立てます。**立てるのはサーバー、読むのは Claude。** 卦辞・爻辞・彖伝のたぐいは一切返しません——返るのは卦名・番号・記号・爻の並びだけで、そこから先は Claude 自身の知識で読みます（六十四卦の名前は古典なので、ここに置いても権利の心配はありません）。

| 引数 | 型 | 既定 | 説明 |
|---|---|---|---|
| `method` | enum | `coins` | 立て方。`coins` / `yarrow` / `abridged` |

3つの立て方は「どのくらい変爻が出るか」が違います。手順ごとシミュレートしているので、確率表から答えを直接引くのではなく、コインの表裏や筮竹の本数も過程として返ります。

| id | 名前 | 手順 | 6/7/8/9 の出方 |
|---|---|---|---|
| `coins` | 擲銭法 | コイン3枚を6回投げる（表=3・裏=2 の合計） | 1:3:3:1。手軽で変爻が出やすい |
| `yarrow` | 本筮法 | 筮竹50本の三変を6回（49本を二分→掛一→左右を4本ずつ数える） | 老陰1/16・少陽5/16・少陰7/16・老陽3/16 の伝統的な偏り |
| `abridged` | 略筮法 | 筮竹で下卦（mod 8）・上卦（mod 8）・変爻（mod 6）を1回ずつ | 変爻はちょうど1本 |

返り値（`structuredContent`）は `method` / `cast_at` / `lines`（初爻から上爻へ6本。`position` `value`(6〜9) `yin_yang` `changing` `label`＝初九・六二…、それに立て方ごとの過程）/ `primary`（本卦：序卦の番号・卦名・Unicode 記号・上下の八卦）/ `changing_lines` / `resulting`（之卦。変爻が無ければ `null`）/ `nuclear`（互卦）。略筮法だけは過程が卦単位なので、爻ではなく `abridged` に載ります。

テキスト出力の形:

```
易（擲銭法）
本卦: 第3卦 水雷屯 ䷂（上: 坎☵ 水 / 下: 震☳ 雷）
爻: 初九（老陽・変） 六二 六三 六四 九五 上六
変爻: 初爻
之卦: 第8卦 水地比 ䷇
互卦: 第23卦 山地剝 ䷖
出目: 3+3+3, 3+3+2, 3+3+2, 3+3+2, 3+2+2, 3+3+2
```

`（老陽・変）` が付くのは変爻だけ。変爻が無いときは `変爻: なし` で止まり、**之卦の行そのものが出ません**。最後の1行は過程のまとめで、本筮法なら `筮竹: 5-4-4→36, …`（三変で除いた本数→残り）、略筮法なら `筮竹: 下卦 4→4, 上卦 6→6, 変爻 1→1` になります。

六十四卦の表は `src/hexagrams.ts` の静的データ（番号・卦名・上下の八卦・記号）。爻のビット列（初爻が bit0・陽=1）で 0〜63 と 1 対 1 に対応させてあり、表の正しさ（64個・番号一意・記号が `U+4DC0+(番号-1)`・序卦が2つずつ対）はテストで固定しています。

#### 納甲（`nakko: true`、断易）

`cast_hexagram` に `nakko: true` を渡すと、筮はそのままに（乱数は増えません）、**立卦日時の四柱**と、本卦・之卦の**各爻の納甲干支・八宮と世応・六親・六獣**を導出して添えます。伏神は付けません。卦辞・爻辞を載せない方針は変わらず、六親の吉凶も言いません——そこは Claude の知識で。

| 引数 | 型 | 既定 | 説明 |
|---|---|---|---|
| `nakko` | boolean | false | 納甲を付ける |
| `year` / `month` / `day` | integer | 現在 | 立卦の日（3 つそろえて指定。`nakko: true` のときだけ） |
| `hour` / `minute` | integer | 0:00 | 立卦の時刻（省略すると **0 時**扱い） |
| `utc_offset` | number | **9** | その時計の時差。省略時は日本時間（公開側ですが、UTC 既定だと日本の深夜に日干支がずれるため） |

算法の決め（2026-08-22、どれも「決めの問題」なので決めてあります）:

- **日界は 0 時**。23:00〜00:59 が子の刻で、23 時台も「その日」の日干支のまま（翌日に繰り上げない）。時干はその日の日干から五鼠遁
- **年と月は節気正確**。同じ Worker の Swiss Ephemeris でその時刻の太陽黄経を 1 回引き、立春（315°）で年を切り、30° ごとに月支を切る（固定表の近似ではない）。月干は年干から五虎遁
- 日干支はユリウス日番号から（2000-01-01 = 戊午で検算）
- 八宮は八純卦から「初爻から順に爻を返す」算法で導く（一世〜五世・遊魂・帰魂。64 卦が各宮に 1 回ずつ現れることをテストで固定）。世爻は本宮 6・一世 1・二世 2・三世 3・四世 4・五世 5・遊魂 4・帰魂 3、応は世から 3 つ隔てた爻
- 六親は宮の五行を「我」として爻の地支五行と比べる。之卦の六親も**本卦の宮**で付ける（断易の慣例）。六獣は日干から初爻に置いて上へ巡る

`structuredContent.nakko` に `pillars`（年月日時の干支）・`palace`（宮・五行・世代）・`self_line` / `other_line`・`lines[6]`（干支・五行・六親・六獣・世応）・`changed_lines`（之卦、変爻があるとき）と `sun_longitude` が入ります。

### `roll_astro_dice`

アストロダイスを振ります。天体（太陽〜冥王星の 10 個＋ノースノード・サウスノード）・星座（牡羊座〜魚座）・ハウス（第1〜第12）の 12 面ダイス 3 個を独立に振り、「天体 × 星座 × ハウス」の組を返します。**振るのはサーバー、読むのは Claude。** 広く知られた体系なので意味テキストは載せず、名前・記号・英名だけです（タロット・ルーンと同じ線引き）。

| 引数 | 型 | 既定 | 説明 |
|---|---|---|---|
| `count` | integer | 1 | 何組振るか（1〜3） |

```
アストロダイス / 1組
1. ☉ 太陽 × ♈ 牡羊座 × 第7ハウス
```

`structuredContent.rolls[]` に `planet` / `sign` / `house` が入ります（`planet` と `sign` は `name` / `symbol` / `name_en`、`house` は `number` / `name`）。

### `cast_geomancy`

西洋ジオマンシーのシールドチャートを立てます。**立てるのはサーバー、読むのは Claude。** 引数はありません。

乱数で決まるのは**母卦 4 つ＝16 点（各行 奇数なら 1 点・偶数なら 2 点）だけ**で、娘（母の転置）・姪（母と娘を 2 つずつ足す）・証人（姪を 2 つずつ足す）・裁判官（証人を足す）は純関数で完全導出です。参考として和解者（裁判官＋第一の母）も添えます。図形は 16 種（Via 道 / Populus 群衆 / Fortuna Major 大吉 / Fortuna Minor 小吉 / Puer 少年 / Puella 少女 / Amissio 損失 / Acquisitio 獲得 / Conjunctio 結合 / Carcer 牢獄 / Tristitia 悲しみ / Laetitia 喜び / Albus 白 / Rubeus 赤 / Caput Draconis 竜頭 / Cauda Draconis 竜尾）で、ラテン名・日本語名・点の並びだけを返し、意味は同梱しません（既知の体系＝Claude 自身の知識で読む）。

`structuredContent` は `mothers[4]` / `daughters[4]` / `nieces[4]` / `witnesses.right` / `witnesses.left` / `judge` / `reconciler`、各図形は `latin` / `name` / `lines`（上から頭・首・体・足、1 点か 2 点）/ `glyph`。裁判官の点の総和は必ず偶数になる（定理）ので、それをテストで固定しています。

### `moon_calendar`

月まわりの暦（朔望・月の星座入り・ボイドタイム・食）を期間でまとめて返します。**計算するのはサーバー、読むのは Claude。** この 1 本だけは**乱数を 1 ビットも使いません**——ここでのサーバーの仕事は「引くこと」ではなく、天体計算と**ボイドの規約を固定すること**です。誕生日も場所も受け取らない（誰が呼んでも同じ答えになる）ので、公開層に置いています。

| 引数 | 型 | 既定 | 説明 |
|---|---|---|---|
| `start` | string | その日 | 期間の頭（`YYYY-MM-DD`）。その日の 0 時から数える。省略すると `utc_offset` の暦での今日 |
| `days` | integer | 14 | 何日ぶん見るか（1〜62＝2 朔望月ぶん） |
| `utc_offset` | number | 9 | どの土地の時計で読むか。返す時刻は全部この時差の現地時刻（`+09:00` の札つき） |
| `voc_bodies` | string | `modern` | ボイド判定の相手天体。`modern`＝太陽・水星〜冥王星の 9 天体 / `traditional`＝太陽・水星〜土星の 7 天体 |

**ボイド（ボイド・オブ・コース）の規約はこの 1 通り**です——月がその星座で相手天体と**最後に exact なメジャーアスペクト**（0 / 60 / 90 / 120 / 180 度）を作った瞬間から、**次の星座に入る瞬間**まで。オーブは取りません（exact ちょうどが境目）。ノードは相手に入れません。⚠ **ボイドの定義は流派で割れます**（相手天体の範囲・オーブを取るかどうか・「その星座を出るまで」と数えるか「次のアスペクトまで」と数えるか）ので、別の流派の表とは時刻が食い違うことがあります。採った規約は `conventions` に名前で入ります。

食は **global**（地球上のどこかで起きるもの）です。場所を受け取らないので「どこで見えるか」は返しません。半影月食も落とさず入れます（`type` で見分けられます）。

期間の頭より前に始まったボイドも、期間の尻をはみ出して終わるボイドも**切らずに実時刻で返します**（開始時点でボイド中かどうかが分かるように）。`moon_at_start` に開始時点の月の星座・度数とボイド中かどうかが入ります。

```
月まわりの暦（朔望・月の星座入り・ボイド・食）
期間: 2026-08-25 00:00+09:00 〜 2026-09-08 00:00+09:00（14 日間）
開始時点の月: 山羊座 20.91°／ボイド中

2026-08-24 15:30+09:00  ［ボイド］山羊座・最後のアスペクト 月 □ 金星（スクエア・2026-08-24 15:30+09:00）／終わりは 2026-08-25 18:02+09:00 の水瓶座入り
2026-08-25 18:02+09:00  ［星座入り］月 山羊座 → 水瓶座
2026-08-27 06:59+09:00  ［ボイド］水瓶座・最後のアスペクト 月 △ 金星（トライン・2026-08-27 06:59+09:00）／終わりは 2026-08-28 04:04+09:00 の魚座入り
2026-08-28 04:04+09:00  ［星座入り］月 水瓶座 → 魚座
```

### `reverse_horoscope`

**配置のほうを先に決めて、その配置になる日を年代範囲から逆に引きます。**「太陽が牡羊座で月が蟹座なのはいつか」という探し方です。astro-viewer（ロリポップの Astro Tool）の「逆引きホロスコープ」の MCP 版で、こちらも**乱数を 1 ビットも使わず、誕生日も場所も受け取りません**（誰が呼んでも同じ答えになる）ので公開層に置いています。**計算するのはサーバー、読むのは Claude。**

| 引数 | 型 | 既定 | 説明 |
|---|---|---|---|
| `conditions` | array | （必須） | `{ body, sign, priority? }` の配列。天体ごとに1本（同じ天体を2回は書けない） |
| `year_from` | integer | （必須） | 探す年代の始まり（西暦・この年を含む。1800〜2200） |
| `year_to` | integer | （必須） | 探す年代の終わり（同上）。両端を含めて**30年ぶんまで** |
| `utc_offset` | number | 9 | どの土地の時計・暦で読むか。候補日はこの時差の暦日、時刻もこの現地時刻 |

`body` は `sun` / `moon` / `mercury` / `venus` / `mars` / `jupiter` / `saturn` / `uranus` / `neptune` / `pluto`（日本語の天体名でも受けます）。ノードやアングルは条件に使えません。`sign` は日本語（牡羊座〜魚座）でも英語の小文字（aries〜pisces）でも構いません。

`priority` は `required`（既定）か `optional`。**候補日を決めるのは `required` だけ**で、`optional` は各候補日に「その日そろっているか」を添えるだけです（並びは成り立つ数の多い順→日付順）。`required` が1本も無ければ断ります。太陽は必須ではないので、月だけ・外惑星だけの条件でも引けます。

- **ほかの天体は疎サンプル＋3次エルミート補間**（水星〜火星は1日おき、木星〜冥王星は4日おき＝`transit_events` と同じ刻み）。補間の上を刻みの1/24で歩いて星座の出入りを拾い、境目は二分法で詰めます。水星〜火星はさらに「4日刻み＋前後3°の余白で当たりを付けてから1日刻みで詰め直す」二段構えです。

手元の Node での実測は、太陽＋月＋水星の10年で天体計算 943回・51ms、いちばん重い「水星だけ・30年」で 4,445回・251ms（どちらも候補日に添える正午の空＝日数×10天体ぶんを含みます）。同じ条件を6時間刻みで総当たりすると1年あたり1,460回×天体の数になるので、二桁ぶん軽い勘定です。`test/reverse-horoscope-real.test.ts` が7通りの条件で総当たり版と候補日を突き合わせています（6時間刻みの総当たりは6時間より短い当たりを落とすので、「総当たりが拾った日 ⊆ 新実装の日」＋「新実装だけが拾った日は6時間未満」の2段で見ています）。

⚠ サンプルの刻みより短い「星座の境をまたいですぐ戻る」動き（境のすぐ内側で留になる形）は原理的に取りこぼしえます。留が境から0.01°以内という珍しい配置でしか起きませんが、穴として書いておきます。

## 占星術層（`POST /astro/mcp`・招かれた人だけ）

カード層とは別の入口で、ホロスコープ（西洋占星術）の天体計算をします。**計算するのはサーバー、読むのは Claude。** 返るのは天体の黄経・ハウス・アスペクトといった座標と角度だけで、「射手座の人は〜」のたぐいの解釈は一切持ちません。エンジンは Swiss Ephemeris の wasm（Moshier モード＝天文暦ファイル不要）で、`src/astro/engine.ts` が唯一の窓口です。

**出生データは台帳が預かります**（2026-08-22 改定。それまでは「原本レス」＝計算に使ったら捨てる方式でした）。`save_chart` に渡した出生データ（年月日・時刻・時差・緯度経度）は、計算済みの座標（天体の黄経と速度・ハウスカスプ・ASC/MC・ラベル・ハウス方式・登録日時）と一緒に KV へ保存されます。誕生日そのものが要る占術（数秘術・宿曜・四柱推命）を `chart_id` から引けるようにするための改めです。

正直に書いておくと、預かるとはつまり **Cloudflare の KV に出生データが載る**ということです（保存時暗号化はされますが、Cloudflare は中身を持ちます）。そのうえでの約束は3つ:

- **使えるのはその鍵を持つ人だけ**（`chart:<user>:<chart_id>` という前置きで人ごとに仕切ってあります）
- **返事には出しません**。どのツールの返却テキストにも `structuredContent` にも出生データの値は載りません（呼び出した側は登録時に自分で渡しているので、読み戻す必要がない）。エラー文にも値は出しません
- **`delete_chart` で座標もろとも消えます**

ハウス方式を変えたいときは `delete_chart` → `save_chart` で登録し直してください（同じ `chart_id` への上書き登録は用意していません）。「いつもの場所」（`default_lat` / `default_lng`）は出生地とは別の覚え書きで、リターン図を立てる土地として本人が預けたものです。

⚠ 改定より前に登録したチャートには出生データが入っていません。`list_charts` が「出生データ: なし」と出すもので、`progressions` と `calculate_numerology` は使えません（`delete_chart` して登録し直せば使えるようになります）。

### URL 鍵（`POST /mcp/<鍵>`）は引退しました（履歴）

2026-08-22 より前は、URL の末尾に鍵を載せる口（`POST /mcp/<鍵>`。KV の台帳 `key:<鍵>` と突き合わせて 401）が入口でした。URL 方式にしたのは、claude.ai と ChatGPT のコネクタが任意のヘッダを付けられないため（Authorization ヘッダ方式だと Web 側から繋げなかった）です。同日に OAuth の入口（次の節）を足して並走させ、claude.ai・ChatGPT・Claude Code の3クライアントで安定を確かめたうえで、**鍵の口はコードごと引退させました**（`/mcp/<何か>` は今はただの 404 です）。

`wrangler.jsonc` の `observability.logs.invocation_logs: false` は鍵の引退後も据え置きです——鍵が URL から消えても、OAuth の `/callback?code=…` や `Authorization: Bearer …` が呼び出しごとの記録に映り得るためです。

役どころ（`role`）は `owner` と `friend` の2つが台帳のレコードに残っていますが、**現在は挙動の差がありません**（`progressions` が `chart_id` 方式になって owner 特権が無くなったため）。既存のレコードとの互換と、将来の友だちのために型と検算だけ残してあります。

### OAuth の入口（`POST /astro/mcp`・Cloudflare Access）

占星術層の唯一の入口です。身元はヘッダのトークン（OAuth）で確かめ、そのトークンは Cloudflare Access（OIDC）で確かめた人に対してだけ出します。中身の層（ハンドラもツールも台帳も）は旧・鍵の口から引き継いだそのままで、変わったのは「誰か」の確かめ方だけです。

```
claude.ai / ChatGPT / Claude Code
  │ OAuth（DCR・PKCE は S256 のみ。実装は @cloudflare/workers-oauth-provider）
  ▼
POST /astro/mcp ──初回のサインイン──▶ Cloudflare Access for SaaS (OIDC)
  │                                   （人の身元はここで確かめる）
  │ 台帳（ASTRO_KV の email:<SHA-256>）に載っていれば通す。無ければ 403
  ▼
占星術層（ハンドラは `src/astro/astro-mcp.ts`・チャート台帳は `ASTRO_KV`）
```

- **二重の門**: Access のポリシー（そもそもサインインできる人）と、Worker 側の許可台帳（`email:<SHA-256>` → `{user, name, role}`）の両方を通った人だけが使えます。台帳に無ければ 403
- **メールアドレスの生の文字列はどこにも置きません**。台帳の鍵名はハッシュ（SHA-256 の hex 小文字。前後の空白を落として小文字にしてから掛ける）で、レスポンスにも自前のログにも出しません
- **台帳のレコードの `user` がチャートの仕切り**です（`chart:<user>:<chart_id>`）。同じ `user`（例: `owner`）を指すレコードなら、どのメールでサインインしても同じ `chart_id` が見えます
- OAuth 面の実装（`src/auth/access-handler.ts` / `src/auth/workers-oauth-utils.ts`）は、同じ作者の保管庫MCPの門番 Worker（vault-gatekeeper）からの複製です。**変えたのは承認画面のブランド文言と import だけ**で、ロジックには手を入れていません
- 初回接続のときに出る承認画面（「このクライアントを許可しますか」）は、サーバー名と説明だけ日本語にしてあります。ボタンなどの文言は手本のまま英語です（複製に手を入れない方針を優先しました）

### `calculate_numerology`

この1本だけは天体を1つも計算しません（乱数も wasm も使いません）。**ここでのサーバーの仕事は「引くこと」ではなく規約を固定すること**です。誕生日を使う占いなので公開のカード層には置かず、鍵つきのこちらだけに置いています（2026-08-22 の線引き）。

生年月日の出どころは2通りで、**どちらか一方**を指定します。両方渡すと「どちらか一方にしてください」、どちらも無いと「`chart_id` か `year` / `month` / `day` を指定してください」と断ります。

- `chart_id` … 台帳が預かっている出生データから読みます（打ち直さなくてよい。出生データを預かっていない古い登録では使えません）
- `year` / `month` / `day` … 生年月日の直接指定。登録せずに一度だけ見るとき用です

ライフパスは流派（還元の規約）が違うと同じ生年月日から違う数が出ます。1986-12-29 は **11 にも 2 にもなり**、実際に別々の LLM が別の数を答えました——それがこのツールの理由です。そこで単一の答えを出さず、名前つきの4経路と途中式を並べて返します（どの経路で読むかは会話の中で、あるいは占われる本人の流派で決めてください）。

| 経路 | 規約 |
|---|---|
| `full_sum` | 生年月日の全桁をまとめて足し、最後の和でマスターナンバーを保持 |
| `component_reduce` | 年・月・日をそれぞれ1桁まで還元してから足し、最後の和でマスターを保持 |
| `component_keep` | 年・月・日を還元するとき、マスターナンバーは保持したまま足す |
| `no_master` | マスターナンバーを認めず、全桁の和を1桁まで還元 |

| 引数 | 型 | 既定 | 説明 |
|---|---|---|---|
| `chart_id` | string | — | 対象のチャート ID。`year` / `month` / `day` とは併用できない |
| `year` / `month` / `day` | integer | — | 生年月日の直接指定。3つそろえる。暦に存在しない日付（2026-02-31 など）は断る |
| `target_year` / `target_month` / `target_day` | integer | 今日 | パーソナルイヤー／マンス／デイの基準日。3つそろえるか、3つとも省く |
| `utc_offset` | number | UTC | 基準日を省いたとき「今日」をどの土地の暦で決めるか（占星術層の流儀に合わせて既定は UTC） |
| `masters` | enum | `11_22_33` | `11_22` にすると 33 を認めず 6 まで還元する |

```
生年月日: 直接指定（値は返事に出しません）
■ 数秘術（生年月日ベース・ピタゴラス式）
ライフパス: 11 / 2 ← 経路で割れています
  full_sum         11 (→2)  全桁の合計 38 → 3+8 = 11（マスター、保持）
  component_reduce 11 (→2)  年 6 ＋ 月 3 ＋ 日 2 = 11（マスター、保持）
  component_keep   2        年 6 ＋ 月 3 ＋ 日 11 = 20 → 2+0 = 2
  no_master        2        全桁の合計 38 → 3+8 = 11 → 1+1 = 2（マスター無し）
バースデー: 29 → 11 (→2)
アティチュード（サンナンバー）: 5（4 経路一致）
パーソナルイヤー 2026: 6（4 経路一致）
パーソナルマンス 2026-08: 5（4 経路一致）
パーソナルデイ 2026-08-22: 9（4 経路一致）
規約: マスター 11/22/33、パーソナルイヤーは暦年起点（1/1 で切り替わる）。名前数秘・ピナクル・チャレンジは範囲外
```

先頭の1行は生年月日の出どころで、`chart_id` で呼んだときは `チャート: ラベル（id）` になります。**直接指定でも生年月日そのものは返事に出しません**——この層の「出生データを返事に出さない」約束に揃えてあります。

4経路が一致するときは1行に畳み、割れているときだけ経路ごとの途中式を並べます。パーソナルイヤーの起点は**暦年**（1月1日で切り替わる）に固定 ——誕生日起点の流派もありますが、v1 はここを動かしません。v1 の範囲は生年月日ベースだけで、**名前数秘（表現数・魂数など）・ピナクル・チャレンジは入っていません**。

途中式には**生まれ年と生まれ月の生の数字を書きません**（還元したあとの値だけで組み立てます）。生まれた日はバースデーナンバーとしてもともと表に出る数なので、そのまま書きます。

`structuredContent` は `source`（`chart` か `direct`）＋ `life_path` / `birthday` / `attitude` / `personal_year` / `personal_month` / `personal_day` / `conventions`（`chart_id` で呼んだときだけ `chart_id` / `label` も付きます）。バースデー以外は `presets`（4経路それぞれ `value` / `reduced` / `is_master` / `steps`）と `agree` / `values` を持ちます。

### `shukuyo` / `shukuyo_compat`（宿曜占星術）

宿曜も誕生日を使うので、公開のカード層には置かず鍵つきのこちらだけにあります。**読みはサーバーに載せていません**——タロット・ルーンと同じ「既知の体系＝名前だけ返す」の線で、宿の意味も吉凶も三九の秘法の解釈も持ちません。返すのは宿の名前と位置と関係の名前だけです。

**採った規約は返り値にも書いてあります**（読む側の LLM が「この鯖はこの流派」と分かって、サーバーの答えを疑わずに済むように）。

| 規約 | 採ったもの | 理由 |
|---|---|---|
| 方式 | **天文方式**（出生時刻の月のサイデリアル黄経 ÷ 13°20′） | 暦方式（旧暦の日付から宿を引く）は採りません。旧暦は 2033年問題のように裁定者のいない未解決の規約を含むため |
| 基準点（アヤナムシャ） | **Lahiri**（`SE_SIDM_LAHIRI` = 1） | 式で出るので天文暦ファイルも恒星ファイルも要らず、Moshier モード固定と両立します（True Chitrapaksha は恒星ファイルが要るので避けました） |
| 宿の数と起点 | **27宿**（牛宿を含まない）、サイデリアル 0° = **婁宿（Ashvini）**の始まり | 『宿曜経』の列挙が昴宿から始まるのは「表の並び」であって、位置の起点ではありません |
| 三九の秘法 | 本命宿を1として数えた距離で、1=命・10=業・19=胎、あとは8つ組「栄・衰・安・危・成・壊・友・親」が3回 | 近距離（1〜9）・中距離（10〜18）・遠距離（19〜27）。表の並びは**対称性で検算**しています（`test/shukuyo.test.ts` の27×27総当たり。A→B が栄なら B→A は必ず親、というふうに組が裏返しで一致すること） |

表記は漢字の宿名・読み・サンスクリット名（ナクシャトラ名）・1〜27 の番号を全部並べます。LLM の学習データはヴェーダ占星術の英語資料のほうが厚いので、両方に届くようにしてあります。

**月は1日でほぼ1宿ぶん動きます。**だから `shukuyo` は**出生時刻を必須**にしていて（時刻不明では引きません）、返り値には宿内の位置・両隣の宿・前後の境界までの距離を必ず添えます——「出生時刻が少しずれると隣の宿」と読む側が言えるように。日運のほうにも、その日のうちに宿が切り替わる時刻を添えます（`swe_mooncross_ut` で、サイデリアルの境界にアヤナムシャを足し戻したトロピカル黄経を探します）。

```
宿曜（天文方式・Lahiri アヤナムシャ・二十七宿）
チャート: わたし（abc12345）
（宿の意味・吉凶はこのサーバーに載っていません。読みはあなた自身の知識で。どれだけ体系を横断し、それらが全て同じ結果を示したとて、合算の根拠にはならない（面白がるのは自由））

■ 本命宿（出生時刻の月）
亢宿（こうしゅく・Swati・15）
宿内の位置: 3°45′ / 境界まで: 前 3°45′・次 9°35′
両隣: 前 角宿（かくしゅく・Chitra・14） / 次 氐宿（ていしゅく・Vishakha・16）
サイデリアル黄経 190.4167°（1 宿 = 13°20′、起点は婁宿）
（月は 1 日でほぼ 1 宿ぶん動きます。宿内の位置が境界に近いときは、隣の宿も併せて見てください）

■ その日の宿 2026-08-22（UTC+9 の暦）
対象の瞬間: 2026-08-21 15:00 UTC / ローカル 2026-08-22 00:00（UTC+9）（時刻の指定が無いので 0 時で見ています）
心宿（しんしゅく・Jyeshtha・18）
…
本命宿から: 距離 4 → 安（あん） / 近距離 / 組 安壊
アヤナムシャ 24.2292°（Lahiri）

□ この日の宿の切り替わり（UTC+9 の暦の 0 時〜24 時）
2026-08-22 18:19（UTC+9） 心宿 → 尾宿（びしゅく・Mula・19）

規約: 天文方式（出生時刻の月のサイデリアル黄経 ÷ 13°20′） / 基準点 Lahiri（SE_SIDM_LAHIRI）/ 27 宿・婁宿（Ashvini）＝サイデリアル 0° / 暦方式（旧暦の日付から宿を引くやり方）は採らない（旧暦は 2033 年問題のように裁定者のいない未解決の規約を含むため）
```

`date` は過去も未来も受けます（日記の日付を後から引き直す用途）。`"YYYY-MM-DD"` なら `date_utc_offset` の暦での0時、`"YYYY-MM-DD HH:MM"` ならその瞬間で見ます。

`shukuyo_compat` の `a` / `b` は、**まず台帳を `chart_id` として引き、載っていなければ宿名として読みます**（サンスクリット名は `hasta` のように `chart_id` の形と見分けが付かないため、実在する登録を優先）。相手の宿名だけで呼べるので、相手の出生データを会話に出さずに相性だけ見られます。

**出生データは返事に出しません**（この層の約束どおり）。出すのは派生値だけ——宿・宿内の位置・サイデリアル黄経までで、**出生時のアヤナムシャは伏せています**。Lahiri は年 50″ ほどで動くので、小数4桁まで出すと値そのものが「生まれた年月」の目盛りになってしまうためです（日運のアヤナムシャは、呼び出した側が日付を指定しているので出します）。

サイデリアル黄経は「トロピカル黄経 − アヤナムシャ」で出しています。Swiss Ephemeris の `SEFLG_SIDEREAL` を立てて計算した値とは 9″ ほど違いますが（黄道面への投影の取り方の差）、1宿 13°20′ に対して 0.02% なので宿の判定には効きません。基準点の設定（`swe_set_sid_mode`）は `src/astro/engine.ts` の初期化直後に一度だけ呼んでいます——`SEFLG_SIDEREAL` を立てた計算にしか効かないので、ホロスコープ側のトロピカル計算は1度も変わりません（`test/shukuyo-real.test.ts` が本物の wasm で確かめています）。

### `four_pillars`（四柱推命）

四柱推命も誕生日を使うので、公開のカード層には置かず鍵つきのこちらだけにあります。**読みはサーバーに載せていません**——通変星も十二運も蔵干も大運も、標準の呼び名を並べるだけで、格局も用神も強弱も吉凶も持ちません。

天体計算は太陽だけです（`swe_calc_ut` 2回＋`swe_solcross_ut` 2回で 1ms 以下）。四柱そのもの（年月日時の干支）は納甲（`src/nakko.ts`）の `fourPillars` をそのまま借りています——日界 0 時・立春 315°・五虎遁・五鼠遁の算法を二重に持たないためです。

**四柱推命は流派で割れるところがとても多い**ので、採った規約は名前で固定し、返り値（`conventions`）とテキストの末尾にも書いてあります。

| 規約 | 採ったもの | 補足 |
|---|---|---|
| 日界 | **0時**（23時台もその日のまま） | 23時台生まれのときだけ「日界23時（子初換日）」「夜子時」の2通りを `alternatives` に添えます。夜子時は「日柱は当日のまま、時柱だけ翌日の日干から五鼠遁した子刻」の定義で固定（同じ語を23時日界の意味で使う本もあるため）。代替の年柱・月柱は出しません（翌日が節入りをまたぐかどうかまで見ていないので） |
| 時刻の補正 | **なし**（経度補正も均時差もかけない） | 標準時のまま時辰を切ります。境ぎわのときだけ印を出します（下記） |
| 節気 | **太陽黄経**（立春 315°、30°ごとに月柱が替わる） | 暦の節入り表を引かず `swe_solcross_ut` で前後2本の節入りを探すので、境の日でも時刻ぶんまで正しく出ます。年柱も立春で切り替えます |
| 蔵干 | **本気・中気・余気を全部並べ**、通変星は本気で代表 | 節入り後の日数で1つを選ぶ**月律分野表は採りません**（日数の割り振りが流派で大きく割れるため）。代わりに節入りからの日数を返すので、自分の表で絞りたい読み手は絞れます |

**時辰の境からの分数は返しません。**境から15分以内のときだけ「どちら側の境に近いか」という粗い印を出します——時支（2時間の幅）と分数を合わせると出生時刻が分単位で復元できてしまうためです。印が出ていたら「時刻補正をかける流派では隣の時柱になり得る」と読んでください。

節入りの探索（`solarTermSpanAt`）は本物の wasm で検算しています（`test/four-pillars-real.test.ts`）——「前の節入り ≦ 出生 ＜ 次の節入り」と「節の帯は29〜32日」を架空の出生日時8点＋1年ぶん12本の節で確かめ、配線側でも同じ形を毎回検算して、外れたら断ります（`swe_solcross_ut` のエラーチェックが壊れているため）。

### `synastry`（シナストリー）

登録済みのチャート2枚を突き合わせて、**シナストリー**（互いの天体の間のアスペクト）と**ハウスオーバーレイ**（相手のハウスに自分の天体がどう入るか）を出します。`a` / `b` はどちらも**呼び出した人の台帳の `chart_id`** で、他人の台帳は見えません——相手のぶんも自分で `save_chart` しておけば、**相手の出生データを会話に出さずに**2人の図を並べられます（`shukuyo_compat` を宿名だけで呼べるようにしたのと同じ狙いです）。

天体は1つも計算しません（`get_chart` と同じで、KV に入っている座標を突き合わせるだけ）。返すのは派生値だけで、**天体の黄経そのものは載せません**——位置が要るときは `get_chart` で1枚ずつ読んでください（1枚の図の中のアスペクトも `get_chart` の持ち場です）。

| 引数 | 型 | 既定 | 説明 |
|---|---|---|---|
| `a` / `b` | string | — | 2枚のチャート ID。同じ ID を2つ渡すと断ります（1枚の図の中のアスペクトは `get_chart`） |
| `orb` | number | 5° | アスペクトのオーブ（0.5〜10°）。止まった図同士なので広めに取るのが通例です |

アスペクトはメジャー5種で、両側とも**10天体＋ASC/MC**の総当たり（ノードはどちら側にも入れません）。在ハウスのほうは**ノード込みの11天体**を、相手の図のカスプで数えます。2枚でハウス方式が違うときは「在ハウスはそれぞれ相手の図の方式のカスプで数えています」と1行添えます。どちらも止まった図なので接近・離反は付きません。

`structuredContent` は `kind` / `a` / `b`（それぞれ `chart_id` / `label` / `house_system`）/ `orb` / `aspects` / `overlays`（`a_in_b` と `b_in_a`）です。**出生データは返事に出しません**（この層の約束どおり）——ここは `publicChart` すら撒かず、出すのはアスペクトと在ハウスだけです。

### `composite`（コンポジット／中点図）

登録済みのチャート2枚から**コンポジット（中点図）**を組み立てます。`synastry` が「2枚の間に線を引く」のに対して、こちらは**2人の関係そのものを1枚の図にする**ものです。採るのは**中点法**——A と B の同じ天体どうしの中点を取ります。**ダヴィソン法ではありません**（ダヴィソンは2人の出生時刻・出生地の中間で図を立て直す別物で、天体の位置も変わります）。

`a` / `b` はどちらも**呼び出した人の台帳の `chart_id`**で、他人の台帳は見えません。`c` に第三者を足すと**三者読み**——A×B の関係図に C がどう関わるかを見ます（`c` は `a` / `b` と同じ ID でもよく、そのときは「本人と関係図の重なり」を見ることになります）。

| 引数 | 型 | 既定 | 説明 |
|---|---|---|---|
| `a` / `b` | string | — | 2枚のチャート ID。同じ ID を2つ渡すと断ります（1枚の図そのものは `get_chart`） |
| `c` | string | なし | 三者読みで足す第三者のチャート ID |
| `orb` | number | 5° | アスペクトのオーブ（0.5〜10°）。止まった図なので広めに取るのが通例です |

天体は**太陽から冥王星までの10個**だけで、**ノードは扱いません**（2人のノードの中点に定まった読みが無いため、位置の一覧にも出しません）。中点図には速度の概念が無いので、逆行の印も付きません。

**ASC とカスプの立て方**が中点図のいちばん割れるところなので、規約は名前で固定して `conventions` に返します。

| 規約 | 採ったもの | 補足 |
|---|---|---|
| `method` | **中点法**（`midpoint`） | ダヴィソンではありません |
| `midpoint` | 短い方の弧の真ん中（`shorter_arc`） | 0°またぎもそのまま扱います |
| `opposition_tiebreak` | ぴったり180°のときは **A から黄経が増える向きに90°**（`clockwise_from_a`） | 対向のときだけ中点が2つに割れるので、規約で片方に決めています（この場合だけ `a` と `b` を入れ替えると答えが180°変わります） |
| `asc`（既定） | **中点 MC から立て直す**（`derived_from_mc_midpoint`） | 中点 MC を ARMC に直し、**2人の出生緯度の平均**（`latitude: mean_of_birth_latitudes`）でハウスを立てます。黄道傾斜は**2人の出生時刻の中間時点**のもの（`obliquity: at_mean_birth_jd`） |
| `asc`（代替） | **ASC も中点・ハウスは30°等分**（`asc_midpoint_equal_houses`） | 出生データを預かっていない古い登録が混ざっているときだけ落ちる簡易方式。エラーにはせず、本文と `conventions` に「簡易方式」と書き添えます（この方式では MC が10カスプと一致しません） |
| ハウス方式 | 2枚が同じならそれ、違えば**プラシーダス（P）** | どちらか片方を採る理由が無いため。簡易方式のときは `E`（イコール）相当 |

立て直した MC が中点 MC と一致するかは**毎回検算**していて、外れたら断ります（`swe_houses_armc` は複製した wrapper 越しに呼ぶので、返り値はこちら側で確かめる約束です）。実測の往復誤差は 1e-13° 台で、`test/astro-composite-real.test.ts` が本物の wasm で押さえています。

### `kyusei`（九星気学）

九星気学も誕生日を使うので、公開のカード層には置かず鍵つきのこちらだけにあります。**読みはサーバーに載せていません**——吉方位も凶方位も相性も持たず、「五黄殺」「歳破」といった札は*計算上の名前*として並べるだけで、吉凶の言葉は1語も足していません。

天体計算は太陽だけです（`swe_calc_ut` 2〜4回＋`swe_solcross_ut` 8回）。年界（立春）と月界（節）は四柱推命と同じ太陽黄経で切り、日盤の陽遁・陰遁に要る**冬至・夏至は `swe_solcross_ut` で2本ずつ（計4本）**探し——対象日の400日前から1本目、その300日後から2本目——その土地の時差で暦日へ丸めます。対象日の前に2本以上・後に1本以上が必ず入る並びになるので、切り替えの甲子日を取りこぼしません。

**出生時刻は任意**です。星は年・月・日で決まるので時刻不明でも引けます（省くとその日の12時を仮に置きます）。ただし**立春・節入りの当日**に生まれた人だけは時刻で星が変わるので、その暦日の 0時 と 23:59 の両方を計算して、違えば両候補を `alternatives` に添えます（`hour` / `minute` を付ければ確定します）。

**九星気学も流派で割れる**ので、採った規約は名前で固定し、返り値（`conventions`）とテキストの末尾にも書いてあります。

| 規約 | 採ったもの | 補足 |
|---|---|---|
| 年界 | **立春**（節分までは1つ前の年の星） | 判定は太陽黄経 315°。本命星は「11 − 数字根」（10 になったら9を引く） |
| 月界 | **節**（太陽黄経30°ごと。0番目の寅月が立春から） | 月の星は年の星の組（一四七／三六九／二五八）で寅月が決まり（八白／五黄／二黒）、以降1か月ごとに1つ下がります。月命星も月盤の中宮も同じ表 |
| 日界 | **0時**（23時台も同じ日） | 四柱推命と同じ |
| 陽遁・陰遁 | **冬至・夏至に最も近い甲子日**で切り替え | 陽遁は冬至側の甲子から一白→二黒→…、陰遁は夏至側の甲子から九紫→八白→…。「最も近い」は暦日の差で測り、前後が同距離（30日）なら**後の甲子**を採ります |
| 閏遁 | **置かない** | 至の間隔は約182日・甲子のずれは±30日なので、切り替えの間隔は180日か240日のどちらかになります。240日の巡りでも特別な挿入をせず、九紫の次はただ一白へ戻るだけ |
| 破（歳破・月破・日破） | その盤の支の**対冲**の方位 | 本来24方位（1支＝30°）ですが、盤が8方位なので**丸めてあります**——四隅の宮では60°のうち30°だけが実際の破に当たります |
| 時盤 | **持たない** | 初版の範囲外 |

⚠ **日盤の切り替えは流派でいちばん割れるところ**です（閏遁を置く流儀・切り替え日の取り方が違う流儀があります）。市販の暦とこのサーバーで日の星が違う日がありうる、と description にも書いてあります。

|---|---|---|---|
| `chart_id` | string | — | 対象のチャート ID。生年月日の直接指定とは併用できない |
| `year` / `month` / `day` | integer | — | 生年月日の直接指定。**3つそろえる** |
| `hour` / `minute` | integer | 12:00 | 出生時刻。**任意**（省くとその日の12時。立春・節入り当日だけ候補が2つ返る） |
| `utc_offset` | number | UTC | 出生地の時差（日本は 9）。直接指定のときだけ使う |
| `date` | string | 今 | 盤を見る日 `"YYYY-MM-DD"`、時刻まで決めたいときは `"YYYY-MM-DD HH:MM"`。過去も未来も可 |
| `date_utc_offset` | number | UTC | `date` と表示に使う時差。日盤の日界（0時）も、至を暦日へ丸める暦もこの土地で見る |

### 天体計算まわりの実装メモ

リターンの瞬間は総当たりで探さず、Swiss Ephemeris の `swe_mooncross_ut` / `swe_solcross_ut` で一発で出します。⚠ ただし wrapper（`src/astro/sweph/sweph-wasm.js`・無改造コピー）のこの2メソッドはエラーチェックが壊れていて（返り値ではなく flags 引数を見ている）失敗しても throw しません。そこで `src/astro/returns.ts` の `crossUt` が「返ってきた jd が探索開始より後か」を必ず検算しています。

進行 ASC / MC はソーラーアークで動かした MC から ARMC を出し、`swe_houses_armc` で立てます（`astro-viewer` の `viewer/calc.js` の作法をそのまま移植）。

年間概要（`yearly_overview`）だけは1年ぶんを1日ずつ見る作りなので、素直に総当たりすると天体計算が約2,900回＝Workers Free の CPU 上限（10ms）を桁で超えます。そこで**日次の状態機械はそのままに、天体位置の供給源だけ**を差し替えました ―― 天体ごとに4〜16日おきの疎なサンプルを取り、3次ラグランジュ補間で日次表を組み立てます（速度は補間の導関数から出すので `SEFLG_SPEED` を付けずに済み、1回あたりの計算も軽くなります）。刻み幅は15年分（2016〜2030）を本物と突き合わせて天体別に決めたもので、補間誤差は 1e-3° 未満（Moshier 暦自身の精度と同じ桁）。天体計算は約355回で、同じ日付に当たる天体をまとめて呼ぶ（Swiss Ephemeris が地球の位置を使い回すので2天体目以降が半額になる）ため、刻み幅はすべて4日の倍数にそろえてあります。それでも Workers 実機の CPU は 15〜42ms（手元の Node の 2〜5 倍）だったので、このサーバーは Workers Paid で動かしています（`wrangler.jsonc` の `limits.cpu_ms`）。総当たり版との突き合わせは `test/astro-yearly-real.test.ts` が**本物の wasm を読んで**毎回検算しています。

`transit_events` は同じ疎サンプル方式を**速度つき（3次エルミート補間）**にしたものです。速い天体（太陽・月・水星・金星・火星）は1日おき、木星〜冥王星は4日おきのサンプルから、10分刻み＋二分法で分単位の時刻を出します（本物を毎tick叩いた総当たりとの差は1分未満）。期間の上限は動く側の組で決まり（`all` 31日／`no_moon` 93日／`outer` 366日）、天体計算は14日・全天体で100回、93日・月なしで501回。当たりようのない枝（外惑星は1年でも数度しか動かない）は掃いた弧を見て丸ごと飛ばします。検算は `test/astro-events-real.test.ts`。

## エンドポイント

| メソッド・パス | 中身 |
|---|---|
| `POST /mcp` | MCP（JSON-RPC 2.0・Streamable HTTP・ステートレス） |

### ChatGPT 側の注意（ツール定義のキャッシュ）

ChatGPT はコネクタ接続時に `tools/list` の結果（ツール名・説明・`deck` の enum）を取り込んで保持し、その後はサーバー側を更新しても取り直しません（`tools/call` しか飛んでこない）。スマホ版の再接続・アプリの入れ直しでも更新されず、取り直せるのは **Web 版の 設定 → プラグイン → 占いMCP → 情報 → 「更新する」** だけです（2026-08-19 tarot_full 追加時に判明）。デッキやツールを増やしたら、デプロイ後にこのボタンを押すこと。

**`cast_hexagram` の追加（2026-08-19）、`roll_astro_dice` / `lenormand` デッキ / `cast_geomancy` / `cast_hexagram` の `nakko` の追加（2026-08-22）でツール定義が変わりました。**占星術層も 2026-08-22 に `transit` / `lunar_return` / `solar_return` へ `orb` 引数が増え、`calculate_numerology` が12本目、宿曜の `shukuyo` / `shukuyo_compat` が13・14本目として増えています（占星術層のコネクタ側＝`/astro/mcp` も「更新する」）。同日夜には四柱推命の `four_pillars` が15本目、シナストリーの `synastry` が16本目、九星気学の `kyusei` が17本目として増えました。2026-08-25 にはコンポジット（中点図）の `composite` が18本目、四柱の多者盤面 `pillars_relations` が19本目として増えています。**同日夜には月まわりの暦 `moon_calendar` が公開層の 6 本目として増えました**（鍵つき側にもスーパーセットで自動的に載るので、コネクタは両方とも「更新する」）。2026-08-26 には `natal_moon_calendar` が**鍵つき層の20本目**として増えています（天体系の科の末尾＝`yearly_overview` の次に入るので、`tools/list` の並びは `synastry` から後ろが1つずつ下がります）。2026-08-27 には逆引きホロスコープ `reverse_horoscope` が**公開層の7本目**として増えました（鍵つき側にもスーパーセットで自動的に載るので、コネクタは両方とも「更新する」）。`draw_cards` の説明文にもデッキの厚さの理由を1文足しているので、デプロイ後に「更新する」を押さないと ChatGPT 側からは易占ツールが見えません。テスト側では `test/mcp.test.ts` 末尾の `FROZEN_TOOLS` が `tools/list` の返り値を丸ごと凍結しているので、うっかり文言を変えるとそこが赤くなります（意図して変えたときだけ literal を更新 → デプロイ → 「更新する」）。

## 解説（`meanings/`）の更新

`src/data/*.json` は**2つの素材の合成物**です。

| 中身 | 正本 | 直す場所 |
|---|---|---|
| カード名・一言（`meaning` 系） | `fortune-site/src/data/*.json` | fortune-site 側 |
| 解説（`explanation` 系） | 占いゴーストの里々辞書 `dic_fortune.txt` | このリポの `meanings/*.json` |

`meanings/` の中身は、`dic_fortune.txt` からカードごとの解説を抽出した JSON です（`sky_meanings.json` は16枚 `{name, message, explanation}`、`enigma_meanings.json` は32枚 `{name, upright:{…}, reversed:{…}}`）。**使うのは `explanation` だけ**で、同梱の `message` は読み捨てます —— 一言の正本は fortune-site 側（体言止め）で、`meanings` 側の `message` はですます調の別物だからです。

更新手順は、`dic_fortune.txt` を直したあと変換スクリプト（`scripts/extract_fortune.py`）で `meanings/` を作り直して同期:

```bash
python scripts/extract_fortune.py <dic_fortune.txt のパス>   # meanings/*.json を上書き
npm run sync:decks
npm test
```

合成はカード名の突合で行い、**名前が見つからない・余る・解説が空**のときはその場で落ちます（生成物が黙ってズレないように）。解説を足しても `tools/list` のツール定義は変わらないので、ChatGPT 側の「更新する」操作は要りません。

sync のあとは `npm test` と `git diff src/data` を見てからコミットしてください（5 ファイルの書き出しは一息ではないので、途中で止まったときは `git checkout src/data` で丸ごと戻せます）。

## 注意

- `src/data/*.json` は生成物。カード名・一言を直したいときは `fortune-site` 側、解説を直したいときは `meanings/` 側を直して `npm run sync:decks`。**例外は `lenormand.json`**——fortune-site に無いデッキなのでこのリポで手書き（sync は自分の 5 ファイルしか書かないので消えない。札は `number` と `playing_card` を持ち、引いた札の出力にも出る）
- デッキ JSON のスキーマは統一されていません（`sky` は `meaning`、`enigma` / `tarot` は `meaning_upright` / `meaning_reversed`、`rune` はカード個別の `has_reversed` を持ち、正逆の無い札は `meaning`）。`decks.ts` の `cardHasReversed` と `draw.ts` の `pickMeaning` / `pickExplanation` がその差を吸収します
- `name_en`（カードの英名）を持つのはタロット系（`tarot` / `tarot_full`）とルノルマンです。意味テキストではないので意味を剥がしたデッキにも残り、引いた札の `name_en` とテキスト出力の括弧併記（例: `ワンドのエース（Ace of Wands）（正位置）`）になります。持たないデッキではキーごと省かれます
- 設計判断の背骨は3本: **乱数と天体計算はサーバー側で**（LLM に「引いたふり」「計算したふり」をさせない）、**解釈層を持たない**（読むのは会話中の LLM）、**権利の門番**（知られている体系は名前だけ、自作デッキは意味ごと。占星術層は鍵つきで、預かった出生データを返事に出さない）
- 想定していない例外が出たときは、中身をそのまま返さず**決まった一文と参照 ID**（`reference_id`）だけを返します（例外の文面に出生データやパスが混ざって会話へ流れないように）。手元で追うときは、その ID を頼りにサーバー側の記録（`console.error` に残るのは参照 ID と例外の種類名だけ）と突き合わせてください
- 公開の入口（`POST /mcp`）には同じ送信元からの連打の見張りがあります（1 分に 60 回まで。超えると 429 と `Retry-After: 60`。Workers の Rate Limiting バインディング `MCP_RATE_LIMIT`。鍵つきの入口と OAuth の口は別枠＝この見張りの外）
- KV から読んだ台帳のレコードは、使う前に形を確かめます（壊れたレコード・古い形のレコードは、そのまま計算に流さず「登録し直し」の案内へ倒す）
